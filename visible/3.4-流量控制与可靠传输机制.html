3.4 流量控制与可靠传输机制

停止-等待 · 后退N帧(GBN) · 选择重传(SR) — 三种ARQ协议全景对比

📐流量控制 & 可靠传输 — 概念区分

🚦

流量控制

控制发送速率，防止接收方缓冲区溢出
链路层：相邻节点间  |  传输层：端到端

手段：停止-等待 / 滑动窗口
✅

可靠传输

保证数据不错不漏，全部准确交付
依靠 ACK确认 + 超时重传

实现：ARQ 自动重传请求
💡 一句话区分  流量控制 = 控速率（别发太快） |  可靠传输 = 保正确（错了重传）

⚖️三种 ARQ 协议 — 核心特征一览

🛑
停止-等待
Stop-and-Wait (SW)
WT = 1   WR = 1
一次只发1帧
等ACK → 再发下一帧
序号只需1比特(0/1)
❌ 信道利用率极低
⏪
后退N帧
Go-Back-N (GBN)
WT ≤ 2ⁿ−1   WR = 1
连续发送多帧
累积确认：ACK n = 0~n都收到
出错 → 重传全部后续帧
⚠️ 误码高时效率暴跌
🎯
选择重传
Selective Repeat (SR)
WT ≤ 2ⁿ⁻¹   WR > 1
只重传出错帧
接收方可缓存乱序帧
NAK 单独请求重传指定帧
✅ 信道利用率最高

🎮滑动窗口交互演示

选择协议，观察发送窗口 & 接收窗口的行为差异。假设 3 比特编号（0~7），发送 0~7 号帧，4号帧出错

📤 发送方窗口  WT=1
📥 接收方窗口  WR=1
已确认 已发送/待确认 可发送 出错/丢失 缓存(仅SR)

📊 传输结果对比（帧4出错）

🎬各协议对"帧4出错"的处理行为

🛑
停止-等待
发送帧4 → 超时未收到ACK
→ 重传帧4
只重传1帧，但本来也只发了1帧
问题不在重传，在等ACK时空闲
⏪
后退N帧
发送0~7连续发送 → 帧4出错
接收方丢弃帧5,6,7（窗口=1，不缓存）
发送方超时 →
重传帧4,5,6,7 全部！
🎯
选择重传
发送0~7连续发送 → 帧4出错
接收方缓存帧5,6,7（窗口>1）
→ 发送NAK·4
→只重传帧4
收齐后按序上交上层

📊三种 ARQ 窗口大小全面对比（n 比特编号）

协议发送窗口 WT接收窗口 WR约束条件确认方式
🛑 停止-等待 SW WT = 1WR = 1— 逐帧确认
⏪ 后退N帧 GBN 1 < WT ≤ 2n−1 WR = 1 WT ≤ 2n−1 累积确认
🎯 选择重传 SR WT > 1 WR > 1 WT+WR ≤ 2n 逐帧确认 / NAK
⚠️ 关键约束  SR 通常取 WTmax = WRmax = 2n−1，若不满足则新旧帧序号重叠，无法区分新帧与重传旧帧

📈信道利用率计算

定义：发送周期内 有效发送数据时长 / 发送周期总时长

🛑 停止-等待协议
U = TD / (TD + RTT + TA)
发1帧等1个RTT，大部分时间空闲等待
⏩ 连续 ARQ（GBN / SR）
若 nTD < TD+RTT+TA
U = nTD / (TD+RTT+TA)
— 或 —
若 nTD ≥ TD+RTT+TA
U = 1（信道满载！）
📌 信道平均传输速率 = 信道利用率 × 信道带宽

🔬GBN vs SR：为什么行为截然不同？

GBN — 接收窗口=1 的代价

🔹 接收方只能按序收帧
🔹 窗口=1 → 只期待下一帧序号
🔹 其他帧序号不对 → 直接丢弃
🔹 发送方超时 → 重传该帧及之后所有
🎯 累积确认：ACK n 代表 0~n 全收齐
这是GBN最核心的特征

SR — 接收窗口>1 的智慧

🔹 接收方可以缓存乱序帧
🔹 窗口>1 → 序号落在窗口内就收下
🔹 帧出错 → 发NAK单独请求该帧
🔹 只重传出错的那一帧
🎯 代价：接收方需缓存+排序
实现复杂，但效率最高

🎯三种协议适用场景 & 选择指南

🛑 停止-等待
信道质量任意 → 效率都低
唯一优势：实现极简单
适合低速、短距离、简单链路
⏪ 后退N帧 GBN
适合信道误码率较低的环境
✅ 连续发送提升效率
❌ 误码高 → 大量不必要重传 → 效率暴跌
🎯 选择重传 SR
适合需要高吞吐量的场景
✅ 信道利用率最高
✅ 只重传出错帧，不浪费带宽
❌ 实现复杂，需要缓存管理

接收窗口WR = 1WR > 1
收帧方式只能按序可缓存乱序
出错行为重传全部后续只重传出错帧
确认方式累积确认逐帧/NAK
最大发送窗口2n−12n−1
① GBN 接收窗口 = 1 → 只能顺序收；SR 接收窗口 > 1 → 可缓存乱序帧
② 积累确认：ACK n 表示 0~n 号帧全部正确收到（GBN核心）
③ SR 窗口约束：WT ≤ 2n−1，否则序号重叠无法区分新旧帧

⑤ 链路层窗口固定 vs 传输层TCP窗口动态可变
